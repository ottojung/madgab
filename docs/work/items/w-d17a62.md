# Remove the remaining per-candidate allocations from approximate search

## Goal

Continue the behaviour-preserving constant-factor work of
[w-7fa26c](w-7fa26c.md) into the invasive half it deliberately handed off
(P5), now that the cheap wins are integrated and a fresh behaviour lock
exists.

## Context

`madgab-approx-runtime` landed as `d8e14cd` on
`post-milestone-acceptance` (agent `a1b2c304`, item
[w-7fa26c](w-7fa26c.md)). Its post-change profile of
`--approximate --top 20` on `congratulations on your promotion`
(`generate_approximate` total 5.22 s at the time) attributed the
remaining cost to:

- the final prune step, dominated by *cloning* the retained `Partial`s
  (each clones a `Vec<ClueWord>` of `String`s plus the path `key`);
- the dedup and key-sort stages, which are `String`-hash and
  `String`-compare bound;
- `extend_fuzzy` (942 280 calls for that target), which clones the whole
  word and cut vectors and grows `key` with `format!` — O(W^2) per path.

The proposed fix is `Rc`-based `Partial` (or interned path keys) so the
beam shares structure instead of copying it. That is the restructuring
the earlier brief told the agent to hand off rather than attempt.

The behaviour lock is `approximate_output_is_locked` in
`tests/corpus_integration.rs`, re-baselined on the integrated tree during
the same pass. `cargo test --release --lib`,
`--test corpus_integration` and `--test exact_determinism` are the
validation commands (`cargo fmt`, `cargo clippy` and doctests do not
exist on this host; see [../../environment-notes.md](../../environment-notes.md)).

## Completion criteria

- Output is bit-identical to the pre-change binary across a spread of
  targets and configurations, demonstrated with a reproducible
  comparison recipe in the handoff and guarded by
  `approximate_output_is_locked`.
- `Partial` state is shared rather than copied on the beam's hot path, or
  the agent has measured and reported evidence that it is not worth it.
- `cargo test --release --lib`, `--test corpus_integration` and
  `--test exact_determinism` show no new failures.
- Before/after wall clock reported for every configuration measured, with
  the known noise caveat of this shared host.
- No phrase-specific hard-coding, and no scoring-semantics change: this is
  a constant-factor item, and the axes in `axes::*` must not move.

## Pass 2026-09-26T15:40Z (agent d17a620): done, integrated as 7faa74c

Branch `madgab-alloc-sharing`, tip **`889923e`** ("Reuse span-path
allocations across candidate scoring"), integrated into

### What changed

All of it is in `src/lib.rs`; `src/approx.rs` and the diversity policy are
untouched, and no `axes::*` constant moved (checked mechanically over the
diff: no line matching `SIMILARITY|NOVELTY|FAMILIARITY|RHYTHM|SHAPE|
CLOSED_CLASS|GAP_COST|MATCHES_PER_SPAN|SPAN_*|SEG_*|LEXICAL_*` is
added or removed).

1. **Span-path prefixes are shared, not copied** (the real win). The
   lexical recovery heap pushed ~8.9M branches per search, and each
   branch copied its prefix twice: once for the heap entry, once for the
   `seen` set. The prefix is now `Rc<[usize]>`, so a branch costs one
   allocation instead of two, and `seen` stores the same `Rc`.
2. **`seen` uses a seedless FxHash** instead of SipHash. It is a pure
   function of the bytes with no per-process seed, and it is only used
   where iteration order is never observed, so it cannot reach the
   output. This is the "interned keys are only safe if equal keys still
   compare equal and tie-break order never depends on allocation
   addresses" caveat from the notes above, discharged explicitly.
3. **`Partial` shares its clue-word list and cut vector** with its
   siblings: a persistent `Rc<WordNode>` list plus `WordIter`, instead of
   cloning a `Vec<ClueWord>` (two `String`s per word) and a `Vec<usize>`
   on every one of the ~907k `extend_fuzzy` calls. `word_count()` is
   O(1) off the list's cached length.
4. **The path key is built in place** — one pre-sized `String` instead of
   two `format!` temporaries, same bytes.

Criterion "Partial state is shared rather than copied on the beam's hot
path" is met, but the sharing that pays is (1) and (2); (3) and (4) are
real and kept, worth little on their own.

### The brief's premise was wrong, and that is the useful finding

The context section attributed the remaining cost to cloning retained
`Partial`s in the prune step. Measured with temporary phase timers on
`--approximate --top 20` for `congratulations on your promotion` (search
~3.4 s), that is not where the time is:

| phase | cost |
| --- | --- |
| lexical recovery enumeration | ~1.95 s |
| beam + prune loop | ~1.50 s |
| span lattice | ~0.06 s |
| structural DP | ~0.02 s |
| `finish` | ~0.01 s |
| **`prune_partials`, 13,171 calls** | **~48 ms total** |
| `matches_at`, 30 calls | ~15 ms |

`prune_partials` is ~1% of the search, not the bottleneck, so the
`Rc`-based dedup idea that motivated this item would have bought nothing
on its own. The timers were diagnostics and were **stripped before the
commit**; the numbers live here, not in `src/`. No profiler (`perf`,
`valgrind`) exists on this host, which is why the attribution had to be
measured rather than read off a profile.

### Behaviour: bit-identical, and re-measured against the shipping base

The claim is stated against **`3d0130a`**, the base this actually landed
on — not the stale `65ce182` the item was filed against, and not the
`d8e14cd` named in the context section.

Comparison recipe (reproducible):

- build the base and the branch as release binaries from `3d0130a` and
  `889923e` respectively;
- for each of 8 configurations (`--approximate --top 20`, `--top 10`,
  `--beam 128`, `--min-word-len 2`, `--per-word-budget 0.8
  --total-budget 2.5`, `--max-rarity 20000`, `--top 5`, and exact
  `--top 10`) times 14 targets, capture stdout (the ranked clue list)
  and stderr (the `search Nms` line) from each binary;
- compare run by run, keyed on the configuration/target pair.

Result: **112/112 runs identical**, including the visible ranked list,
not merely the scores. The branch was also re-run across three separate
processes per target: stable. `adfc7c4`'s intentional change to the
visible list (the `Clue::cuts` alignment, which re-baselined
`approximate_output_is_locked`) therefore shows up as a difference

is the evidence that the allocation sharing is not entangled with
selection order.

One caution for whoever re-runs this recipe: an interrupted
`compare.sh` leaves a background process writing the same output file,
and the interleaved result looks exactly like a real behaviour
