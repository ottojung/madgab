# Guard approximate-mode run-to-run determinism and top-n stability

## Goal

Approximate mode is a user-facing generator, so two properties it should
have are currently unasserted and are exactly the kind of thing the
scoring work in [w-04f83f](w-04f83f.md) and the sharing work in
[w-d17a62](w-d17a62.md) can silently break while it is in flight:

1. **Run-to-run determinism.** Two runs of the same binary on the same
   target with the same options return the same proposals in the same
   order.
2. **Prefix stability.** Raising `--top-n` does not remove or reorder
   proposals that a smaller `--top-n` already showed.

Both are external behaviour a user can observe and neither depends on how
the search is implemented, so both belong at the executable or public-API
boundary in `tests/`.

## Context

Determinism has been fought for repeatedly in this repository and is
already a stated design goal: `HashMap` iteration order leaked into
results until the exact-mode front fixed it
([w-5d03af](w-5d03af.md)), and the beam retention is deliberately
deduped-and-sorted so it stays deterministic. `tests/exact_determinism.rs`
covers exact mode only. Approximate mode is the branch that actually uses
`HashMap`/`HashSet` in its retention and dedup paths and its beam sorts
against a cached `metrics` vector, and it has no equivalent guard.

Measured on `post-milestone-acceptance` at 45419a7 by this pass, so the
starting position is known:

- `madgab --approximate --top 5 "I love you"` twice in a row: proposal
  lines byte-identical (the only difference between the two files is the
  `search NNNms` timing line in the header). Determinism holds today for
  that one case.
- `--top 5` vs `--top 50` for the same target: the five `--top 5`
  proposals are all still present in the `--top 50` list, but the order
  of the first five is *not* the same, and `--top 50` inserts
  `i.'s a view` and `eye a view` between `aisle a view` and
  `isle come view`. `--top-n` feeds the retention budget, so the search
  does not simply truncate a fixed ranking.

That second point is a design question, not obviously a defect: a budget
that scales with the request is defensible. This item's job is to find out
which of the two behaviours the code *intends*, and then assert the
intended one. If the honest answer is that `--top-n` may reorder results,
record that reasoning here and assert only determinism plus
monotonicity of *membership*, which is the property a user can rely on.

## Completion criteria

- A test in `tests/` asserts that two approximate runs of the same target
  and options return identical proposal lists, for at least three
  targets and at least two `top_n` values, including one multi-sentence
  target and one of the itinerary's canonical inputs.
- A test asserts the `top_n` relationship that the code actually
  guarantees (prefix equality, or membership monotonicity), and the
  handoff explains which was chosen and why, with the measurement above
  as the starting evidence.
- If either property does not actually hold today, that is a finding, not
  a licence to change search behaviour: report it, name the mechanism, and
  file the fix as a separate work item rather than changing scoring,
  retention constants or the axes in this item.
- `cargo test --release --lib`, `--test corpus_integration` and
  `--test exact_determinism` show no new failures. Keep the new tests
  cheap: assert on small `top_n` values and reuse one generator/corpus
  load per test where the existing helpers allow it.
- No phrase-specific hard-coding. Referencing a canonical target string in
  a test is fine; special-casing one in `src/` is not.
- Work is on a focused branch off `post-milestone-acceptance` and is
  integrated by a coordinator, never into `main`.
