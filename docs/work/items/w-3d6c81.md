# Guard approximate-mode run-to-run determinism and top-n stability

## Goal

Approximate mode is a user-facing generator, so two properties it should
have are currently unasserted and are exactly the kind of thing the
scoring work in [w-04f83f](w-04f83f.md) and the sharing work in
[w-d17a62](w-d17a62.md) can silently break while it is in flight:

1. **Run-to-run determinism.** Two runs of the same binary on the same
   target with the same options return the same proposals in the same
   order.
2. **Prefix stability.** Raising `--top-n` does not remove or reorder
   proposals that a smaller `--top-n` already showed.

Both are external behaviour a user can observe and neither depends on how
the search is implemented, so both belong at the executable or public-API
boundary in `tests/`.

## Context

Determinism has been fought for repeatedly in this repository and is
already a stated design goal: `HashMap` iteration order leaked into
results until the exact-mode front fixed it
([w-5d03af](w-5d03af.md)), and the beam retention is deliberately
deduped-and-sorted so it stays deterministic. `tests/exact_determinism.rs`
covers exact mode only. Approximate mode is the branch that actually uses
`HashMap`/`HashSet` in its retention and dedup paths and its beam sorts
against a cached `metrics` vector, and it has no equivalent guard.

Measured on `post-milestone-acceptance` at 45419a7 by this pass, so the
starting position is known:

- `madgab --approximate --top 5 "I love you"` twice in a row: proposal
  lines byte-identical (the only difference between the two files is the
  `search NNNms` timing line in the header). Determinism holds today for
  that one case.
- `--top 5` vs `--top 50` for the same target: the five `--top 5`
  proposals are all still present in the `--top 50` list, but the order
  of the first five is *not* the same, and `--top 50` inserts
  `i.'s a view` and `eye a view` between `aisle a view` and
  `isle come view`. `--top-n` feeds the retention budget, so the search
  does not simply truncate a fixed ranking.

That second point is a design question, not obviously a defect: a budget
that scales with the request is defensible. This item's job is to find out
which of the two behaviours the code *intends*, and then assert the
intended one. If the honest answer is that `--top-n` may reorder results,
record that reasoning here and assert only determinism plus
monotonicity of *membership*, which is the property a user can rely on.

## Completion criteria

- A test in `tests/` asserts that two approximate runs of the same target
  and options return identical proposal lists, for at least three
  targets and at least two `top_n` values, including one multi-sentence
  target and one of the itinerary's canonical inputs.
- A test asserts the `top_n` relationship that the code actually
  guarantees (prefix equality, or membership monotonicity), and the
  handoff explains which was chosen and why, with the measurement above
  as the starting evidence.
- If either property does not actually hold today, that is a finding, not

- `cargo test --release --lib`, `--test corpus_integration` and

### Which top_n relationship the code guarantees: membership, not prefix

Determined by reading the search, not by assuming:

- `--top-n` is not a truncation of a fixed ranking. It feeds the
  retention budget twice in the approximate search (`src/lib.rs`:
  the per-level `keep` and `final_keep` are
  `top_n * 128` clamped to `[1024, 8192]`), and it feeds
  `select_diverse` (`src/lib.rs:2243`), whose representative step only
  looks inside the cutoff `order[..top_n]` and whose share cap is
  `share_cap(top_n, available)` = `ceil(top_n / STRUCTURE_FLOOR)`.
  A larger request therefore searches a *different pool* and selects
  under a *different rule*.
- Consequently prefix equality is not promised, and measurement
  confirms it fails. Measured with the release binary on 7 targets × 4
  `(n, m)` pairs = 28 pairs: **prefix equality held in only 10 of 28**,
  and failed in every pair for 5 of the 7 targets. For "I love you",
  `--top 5` and `--top 10` share all five phrases, but `--top 10`
  inserts `why a view` and `high a view` after `eye a view` and ranks
  the shared `isle come view` / `i'll come view` below how `--top 5`
  shows them. This reproduces the starting measurement in this item
  ("the first five are not in the same order") and extends it.
- **Membership monotonicity held in 28 of 28 pairs**: every proposal
  shown at `--top n` was still shown at `--top m` for `m > n`, at every
  one of the 4 `(n, m)` pairs tried per target. The mechanism is that
  both knobs move monotonically with `top_n` — pruning keeps the
  best-scoring `K`, so a bigger budget yields a superset of candidates;
  the representative step's cutoff grows; the share cap
  `ceil(top_n / STRUCTURE_FLOOR)` grows with it. A bigger request can
  add and reorder, but is not expected to retract.
- So the asserted property is **membership monotonicity**. The test does
  not assert prefix equality and does not assert anything about ranks or
  scores, so it survives a legitimate re-scoring by
  [w-04f83f](w-04f83f.md).

### What was added

`tests/approx_determinism.rs`, two tests:

- `approximate_mode_is_reproducible_across_processes` — same target and
  options across two real subprocesses (fresh hash seed each) give
  identical proposal lists in identical order, for 4 targets × 2
  `top_n` values (3 and 5). Targets are the canonical "I love you" and
  "recognize speech", the full sentence "It's just a stupid game", and
  the short "taco cat". Only the phrase of each proposal line is
  compared, so timing lines and scores cannot make it flaky. Subprocess
  rather than in-process is deliberate: the risk is a `HashMap`/`HashSet`
  iteration order reaching the answer, which is a property of the
  process hash seed and is invisible to any in-process test. That is
  the same reasoning as `tests/exact_determinism.rs`.
- `raising_top_n_does_not_retract_shown_proposals` — the membership
  property, at the public-API boundary, over the same 4 targets × 3
  `(n, m)` pairs (`3→5`, `3→8`, `5→8`). One `Generator` is built once
  and `set_config` flips `top_n`, so the corpus load and fuzzy-lexicon
  build are paid once for the whole test; `top_n` is kept small
  deliberately because the retention budget floors at 1024 regardless,
  so a larger `top_n` costs search time and tests nothing new.

Both properties hold today, so no follow-up is needed for either.
