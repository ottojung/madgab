## Goal

Replace the uniform per-slot enumeration cap in the approximate traversal with a **per-slot,
depth-aware width allocation** derived from the actual emission budget, so that shallow slots
(the depth-1 slot first) can afford more per-slot width than deep slots, instead of every slot
being clamped to the same figure.

The motive is measured, not hypothetical. Canonical case 2
(`It's just a stupid game` -> `Hits Justice Dupe Hid Came`, depth 5) is **one index** outside the
current cap: the depth-1 word sits at traversal index `7`, the cap is
`LEXICAL_BRANCH_STAGE_0 = 7`, and the walk's test is `index < cap`, so `7 < 7` is false. Full
enumerability of the same five slots would need width `100` (the depth-4 slot's word is at index
`99`), i.e. roughly **14x** the number the current derivation produces. The per-slot floors across
the six admission passes are `7/0/3/85/7`; no re-specification of admission can beat them, so the
only remaining upstream mechanism is the width rule itself.

## Why the current derivation cannot simply be corrected

Two independent findings say the number is not a tuning mistake but a category error:

1. **It is a budget figure used as an enumeration cap.** `affordable_opening_width` divides the
   per-segmentation allowance by the cost of *pushing one candidate*; the traversal then uses the
   result as a per-slot *list prefix length*. Those are different quantities, and the equality
   between them is what caps the clue out.
2. **The table the derivation rests on is wrong.** At depth 5 slot 1 the affordable width is
   **10** (3,998 <= 4,000), not 7, so the row is 9/10/10/10/list - monotone - while the recorded
   9/7 *decreases*; the depth-6 last-slot cost is 3,906, not 2,801; and the accompanying test's own
   `assert_eq!(previous, 160)` refutes the "93" in its own doc comment. See
   [../REPORT-4b1e07.md](../REPORT-4b1e07.md) (HOLD, at `b620934`).

So the front must **re-derive** the width in the right units rather than patch a constant.

## Hard constraint discovered by the previous front: traversal-index units

The walk does **not** index the shortlist. `slots[k]` is `edge.matches` **re-sorted by
`SlotAlt::contribution(word_count)`** (familiarity/shape/closed-class divided by slot count,
`WORD_NOVELTY / word_count`, ties by word), and `cap` bounds *that* list. Because
`contribution` divides by the slot count, **a wider slot is a differently-ordered list, not a
longer prefix** - measured movements: `it` 143 -> 0, `wreck` 32 -> 1, `came` 7 -> 11, `hid` 85 -> 99.
Any width rule must be stated and validated in traversal-index units, per depth, and must not be
argued in shortlist-index units. `cap` is a bound on the third of four distinct per-slot orders
(admission, shortlist, traversal, per-pass); the shortlist order is not what stands in the way.
