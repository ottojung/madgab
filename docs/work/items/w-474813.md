# Two follow-ups from the accepted D6c review: the unpinned axis floor, and the pool
# size that did not stay put

## Why this item exists

[w-9d4e10](w-9d4e10.md) delivered the per-phone `SIMILARITY` charge (D6c) and
was reviewed adversarially by `d1c8f1` under [w-d1c8f](w-d1c8f.md). The verdict
was **pass-with-follow-up**, and it was integrated as `33a46f1` on
`post-milestone-acceptance`. Two findings from that review were explicitly
*not* treated as blockers but are real, are still true on the integrated tree,
and would otherwise be lost:

### F1 — the pool is not unchanged, and the one instruction that was not carried out

[w-5c11a2](w-5c11a2.md) specified that D6c should leave the candidate pool size
unchanged. It does not. The reviewer measured **18,242 -> 18,270** and
**18,917 -> 18,936**. `SIMILARITY_COST_PER_PHONE = 0.30` rescales the `SIMILARITY`
term, so it also changes which candidates clear the score cutoff and therefore
the pool. The implementer did not perform the check that would have shown this,
and w-9d4e10 recorded the pool prediction as *unmeasured*.

This matters beyond bookkeeping: the whole case-2 objective argument in
[w-7c1f64](w-7c1f64.md) is priced against a specific pool size and a specific
rank-50 cutoff. Both moved. Any later claim of the form "case 2 is N ranks away"
must be re-measured on the integrated tree, not carried over.

### F2 — the `SIMILARITY` axis's `0.0` floor is no longer pinned by any test

The test deleted by w-9d4e10,
`similarity_is_scored_per_word_not_per_candidate`, was reviewed and its deletion
accepted — its claim (flat in word count at equal *per-word* cost) is the
literal negation of the D6c specification, and it is red in the new tree. But
one thing it did incidentally was pin the axis at a `0.0` floor. Its replacement,
`similarity_is_charged_per_phone_not_per_word`, does not. Nothing now asserts
that `similarity` stays inside `[0.0, 1.0]` or that it reaches `0.0` for a
sufficiently dissimilar candidate. The production code does `.clamp(0.0, 1.0)`,
but a clamp with no test is a convention, not an invariant.

### F1 — measured. The brief's four numbers are all confirmed exactly.

**One correction to the brief's premise first, because it changes how the
numbers below were obtained: there is no `MADGAB_TRACE_PHRASES` /
`MADGAB_TRACE raw_cutoff` hook in this tree.** No `env::var` of any kind is
read by `src/` or `src/main.rs`; the only environment read anywhere in the
repository is `APPROX_POOL_HELPER_TARGET` in `tests/approx_determinism.rs`,
which selects a helper test and is not a trace facility. The shipped
`madgab` binary prints no pool size and no rank-*k* cutoff under any flag.
Whatever the D6c review used to get 18,242/18,270/18,917/18,936, it was not
a shipped hook on this head, and "confirm on this head" had to be done
another way.

The way that works is already public: `Generator::generate_pool` returns the
whole score-ordered deduplicated pool, so both the pool size and the score
at rank 50 are readable from outside the crate. Measured with a throwaway
`examples/` harness on that public API (removed again; not committed), in
release builds, against the pre-D6c base `36589f8` in a scratch worktree so
the delta is measured rather than quoted:

| target | pool @36589f8 | pool @204e6eb | rank-50 cutoff @36589f8 | rank-50 cutoff @204e6eb |
|---|---|---|---|---|
| `It's just a stupid game` (case 2) | **18,917** | **18,936** | 0.917129 | **0.915122** |
| `recognize speech` (case 1) | **18,242** | **18,270** | 0.917026 | 0.918796 |

Both pool figures match the review's numbers to the candidate, so the
reviewer's measurement stands and is reproducible on this head. The two
targets were never labelled in the brief; 18,270 is case 1 and 18,936 is
case 2, and that is now on the record.

**The rank-50 cutoffs are the part the review did not report, and they are
the number the case-2 objective argument is actually priced against:**

* case 2, `It's just a stupid game`: pool 18,917 -> 18,936 (**+19, +0.10%**),
  but the rank-50 score cutoff **fell** 0.917129 -> 0.915122, i.e. **-0.002007**.
  The pool grew *and* got cheaper at the margin. D6c made a small number of
  bad candidates newly eligible, and it did so at the bottom of the
  retained set, not near rank 50.
* case 1, `recognize speech`: pool +28 (+0.15%) and the cutoff **rose**
  0.917026 -> 0.918796, i.e. +0.001770. The opposite sign on the same change.

So D6c did not simply "widen the pool". It reshuffled the lower tail in both
directions, differently per target. The two effects are small and go in
opposite directions on the two canonical targets, which means they largely
cancel in any aggregate and neither is a meaningful lever on its own.

**Is the pool growth undesirable in its own right? On this evidence: no, and
it is bounded, but it is not free either.** Reasons:

* The growth is 0.10% and 0.15% of pool. It is not a blow-up, it is not
  order-of-magnitude, and it is two orders of magnitude smaller than the
  emission-side deltas the project already tolerates. The pool is a
  search-space fact, not a user-visible one: the printed list is unchanged
  in size, and `generate_pool`'s own doc comment is explicit that a
  run-to-run pool delta of one leaves the visible `top_n` byte-identical.
* But it is not zero, and the honest reading of it is that **w-5c11a2's
  stated invariant ("D6c should leave the pool size unchanged") is false
  and should be struck rather than defended.** The mechanism is already
  understood and was not in dispute: `SIMILARITY_COST_PER_PHONE = 0.30`
  rescales the `SIMILARITY` term, which changes which candidates clear the
  score cutoff, which changes pool membership. Any change to the similarity
  normaliser will do this. It is not a bug to be bounded; it is a coupling
  that a claim like "D6c does not affect the pool" must simply not make.
* What would be a real problem, and is not present: a growing pool that
  pushed the rank-50 cutoff *down* materially would mean D6c was buying
  reach with unearned quality, and the canonical case 2 is the one where
  that would show. It moved -0.002, about one printed digit at three
  decimals and well under the granularity `approximate_output_is_locked`
  prints, which is consistent with that test staying green.

**Current denominator for any future case-2 "N ranks away" claim: pool
18,936, rank-50 cutoff 0.915122.** The shipped binary's own printed 50th
line for the same invocation (`madgab --approximate --top 50 "It's just a
stupid game"`) reads `[0.913] it josh test oop add aim`, which is *not*
the same number: the printed list is post-`select_diverse`, so the printed
rank 50 and the pool rank 50 are different objects. Quote the pool number
for reachability arguments and the printed number only for output claims.

**Wall clock**, release build, single invocation each, single core, on the
same host, from `./target/release/examples/zz_measure_pool`:
case 2 pool build 0.857 s; case 1 pool build 0.800 s; pre-D6c base 0.911 s
(case 2) and 1.002 s (case 1). Whole-process `real` including corpus load
was ~1.4-1.7 s in every case. The shipped binary for case 2 was
`real 0m1.634s`. **D6c is not a measurable runtime cost**; the ~6% spread
between the pre-D6c and current numbers is within the noise of four
single-shot timings and should not be quoted as a speedup.

### F2 — done. New test `similarity_axis_is_bounded_and_reaches_both_ends`.

`src/lib.rs`, in the metrics unit-test module, immediately after
`similarity_is_charged_per_phone_not_per_word`. It asserts that the
`SIMILARITY` axis value read off `Partial::metrics` — the same scorer every
pooled candidate goes through —

1. equals `1.0` for a zero-edit-cost candidate (the ceiling is *reached*,
   not merely respected);
2. equals exactly `0.0` for a candidate far outside the target's phonetics
   (the floor is *reached*); and
3. stays in `[0.0, 1.0]` and is non-increasing in edit cost across a
   65-rung geometric ladder of costs from free to far past the floor.

**Boundary choice, and why not a test in `tests/`.** `Metrics` is private
and there is no public per-axis accessor anywhere in the crate, so nothing
in `tests/` can read `similarity` at all. The nearest boundary that
exposes the value is `Partial::metrics`, and that is also where the sibling
per-phone test lives. So the assertion is on the **value the scorer
produces**, not on the mechanism: nothing in the test mentions `.clamp`,
and it would pass unchanged against a `min`/`max` pair or a saturating
subtraction. It names no constant — the floor case is "dissimilar enough",
and where exactly the floor sits is `SIMILARITY_COST_PER_PHONE`'s business.
The non-monotonicity leg is the substantive one: it is what stops a future
"refinement" of the axis from quietly inverting it.

**Red before, green after — with the honest caveat that there is no
accompanying production change to make it red.** The `.clamp(0.0, 1.0)` was
already in `metrics` when this item was written, so the new test is green
as committed. Rather than claim a red-to-green transition that never
happened, non-vacuity was established by mutation: with the clamp
temporarily deleted from `metrics` (leaving the bare
`1.0 - cost_per_phone / axes::SIMILARITY_COST_PER_PHONE`), the new test
**fails** at the `0.0`-floor assertion; with the clamp restored it passes.
The clamp was restored and the committed diff is test-only. That is what
"a clamp with no test is a convention, not an invariant" is asking to be
closed, and it is closed: the invariant is now red the moment it stops
holding.
