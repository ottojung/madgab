## Hypotheses worth testing first, in order

1. **The per-slot depth profile is the constraint.** The reserve now walks slot
   subsets breadth-before-depth, so a word *is* reachable in each slot
   individually, but the emitted tuples may never place two deep coordinates in
   the *same* structure. A pairing needs more than one slot off the traversal's
   best index at once. `coverage_tuples` already has an `EMIT_PROFILE_MAX_DEEP`
   of 3 and subsets up to size 3; the question is whether the budget
   (`EMIT_PROFILE_RESERVE`) or the ordering is what keeps the requested shape
   out, and which.
2. **The cost bound rejects the tuple, not the ordering.** `build` compares each
   tuple's total substitution cost against `total_budget` additively. If the
   requested tuple's cost exceeds the budget while each of its words
   individually does not, then the per-slot affordability slack
   `sum_{j != k} m_j + cost_{k,i} <= total_budget` — the arithmetic
   [w-4b1e07](w-4b1e07.md)'s 11:52Z pass derived — is the real gate, and the
   fix is to make the *pair's* affordability visible to the traversal rather
   than each word's.
3. **The structure's own retention is the gate.** 47 members is small; check
   whether `SEGMENTATION_KEEP` or the pool's per-structure cap is what holds it
   at 47, and whether a structure that is *under*-represented is being
   crowded out of the pool by structures with more members.
